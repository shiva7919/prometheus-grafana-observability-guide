Observability vs Monitoring (SRE perspective)

Control theory, SLIs/SLOs, and why observability is a system property
📡 Monitoring

Predefined metrics + thresholds. Answers "Is something wrong?" Relies on known failure modes.

🔬 Observability

Explore unknown failure modes using metrics, logs, traces. Answers "Why is it wrong?" Based on control theory – system is observable if internal state can be inferred from outputs.

🎯 SRE metrics

SLIs (e.g., latency, error rate), SLOs (e.g., 99.9% availability), error budget. Observability helps reduce MTTD/MTTR.

Monitoring asks “what”; observability enables “why” via high‑cardinality telemetry.

Instrumentation – the foundation

Auto/manual, context propagation, semantic conventions
📌 What is instrumentation?

Embedding code to emit telemetry. Without it, the system is black box. OpenTelemetry provides vendor‑neutral SDKs and semantic conventions (e.g., http.method, db.system).

🧩 Auto‑instrumentation

Zero‑code changes: attach agent (Java, Python, Node.js) to capture common libraries (HTTP, gRPC, DB). Ideal for getting started.

✍️ Manual instrumentation

Custom spans, metrics, logs. Example: adding business‑critical operations as spans, setting custom attributes (user.id, payment.amount).

🔄 Context propagation: W3C `traceparent` header ensures trace continuity across services. Always inject/extract.
4

Grafana – unified visualisation

Frontend, datasources, alerting, correlations
🏗️ Architecture

React frontend + Go backend. Data source plugins (Prometheus, Loki, Tempo) communicate via HTTP. Alerting engine evaluates rules periodically.

🔗 Derived fields (trace‑log link)

In Loki datasource: add field name traceID, regex traceId=(\w+), URL ${__value.raw}, data source Tempo. Now every log line containing a trace ID becomes a clickable link to the full trace.

5

Prometheus – metrics & PromQL

TSDB, WAL, recording rules, RED/USE
📖 Internals

Discovery → Scrape → TSDB (2h blocks, WAL) → Query. Retention: 15d default. For long‑term, use Thanos or Mimir on object storage.

🚀 PromQL essentials

rate(http_requests_total[5m]) – per‑second rate
histogram_quantile(0.99, sum(rate(request_duration_bucket[5m])) by (le)) – P99 latency
sum by(service) (rate(errors_total[5m])) / sum by(service) (rate(requests_total[5m])) – error ratio.

🎯 RED & USE

RED (Rate, Errors, Duration) for services; USE (Utilisation, Saturation, Errors) for resources.

6

Alertmanager – smart alert handling

Grouping, inhibition, silences
⚙️ Processing

Prometheus sends alert → Alertmanager groups (by alertname, cluster) → inhibits low‑priority alerts (e.g., disk full when node down) → silences (maintenance) → routes to receivers (Slack, PagerDuty, webhook).

yaml
route:
  group_by: ['alertname','namespace']
  group_wait: 30s
  repeat_interval: 4h
  receiver: 'pagerduty'
inhibit_rules:
  - source_match: {severity: 'critical'}
    target_match: {severity: 'warning'}
    equal: ['instance']

Loki – cost‑effective logs

Index only labels, LogQL, object storage
🏗️ Components

Distributor (hash labels) → Ingester (write chunks to Azure Blob) → Querier (read from store + index gateway). Compactor deduplicates and retains.

📝 LogQL examples

{namespace="prod"} |= "error"
rate({app="api"} | json | level="error" [1m])
{traceID="abc123"} → correlation.

8

Tempo – scalable tracing

No indexing of tags, block storage, TraceQL
🗄️ Storage

Traces stored as blocks in Azure Blob. Only `trace_id` is indexed. Cost = $/GB, no expensive tag indexes. Query by TraceID or use TraceQL with Bloom filters.

📊 Service graphs

Tempo's metrics generator computes service dependency graphs and span metrics (rate/errors/duration) without modifying apps.

AKS setup & Workload Identity

Azure Blob storage, managed identities, federation
bash
az group create -n myRG -l eastus
az aks create -g myRG -n obs-cluster --node-count 2 --enable-workload-identity
az aks get-credentials -g myRG -n obs-cluster

# Storage account & containers
az storage account create -n mystorage -g myRG --sku Standard_LRS
az storage container create --name loki-data --account-name mystorage
az storage container create --name tempo-data --account-name mystorage

# Managed identities
az identity create -g myRG -n loki-id
az identity create -g myRG -n tempo-id

# Assign Storage Blob Data Contributor
STORAGE_ID=$(az storage account show -n mystorage -g myRG --query id -o tsv)
az role assignment create --assignee $(az identity show -g myRG -n loki-id --query principalId -o tsv) --role "Storage Blob Data Contributor" --scope $STORAGE_ID
# repeat for tempo-id

# Federate identity to K8s service account
export OIDC_ISSUER="$(az aks show -g myRG -n obs-cluster --query oidcIssuerProfile.issuerUrl -o tsv)"
az identity federated-credential create --name loki-federated --identity-name loki-id -g myRG --issuer $OIDC_ISSUER --subject system:serviceaccount:loki:loki
# same for tempo

# Annotate service accounts
kubectl create ns loki
kubectl annotate serviceaccount -n loki loki azure.workload.identity/client-id=$(az identity show -g myRG -n loki-id --query clientId -o tsv)

Sample instrumented app (Python)

Flask + OpenTelemetry, logs with trace_id, metrics
python
# app.py
from flask import Flask
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.instrumentation.flask import FlaskInstrumentor
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
import logging, time, random

logging.basicConfig(level=logging.INFO,
    format='{"time":"%(asctime)s","level":"%(levelname)s","msg":"%(message)s","trace_id":"%(otelTraceId)s"}')

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter(endpoint="otel-collector:4317", insecure=True)))
trace.set_tracer_provider(provider)

app = Flask(__name__)
FlaskInstrumentor().instrument_app(app)

@app.route('/slow')
def slow():
    tracer = trace.get_tracer(__name__)
    with tracer.start_as_current_span("slow") as span:
        delay = random.uniform(1, 3)
        span.set_attribute("delay", delay)
        time.sleep(delay)
        logging.warning("slow request took %.2fs", delay)
        return f"waited {delay}s"

Incident response walkthrough

500 errors → alert → exemplar → trace → log → RCA
🔥 Scenario

Error rate spikes to 10%. Alert `HighErrorRate` fires (Prometheus rule).

Step 1: Grafana dashboard shows error rate per endpoint – `/payment` is culprit.
Step 2: Click exemplar on metric panel → opens Tempo trace.
Step 3: Trace shows `payment-service` calling external bank API with 4s timeout (normal 200ms).
Step 4: In trace, click “Logs for this span” → Loki returns logs with same trace_id: “bank API timeout, retries exhausted”.
Step 5: Root cause: external dependency throttling. Remediation: circuit breaker + fallback.

Production best practices & cost

Cardinality, sampling, retention, security
🏷️ Cardinality control

Never use labels with unbounded values (user_id, trace_id). Use recording rules to aggregate.

🎚️ Sampling

Tail‑based sampling in OTel Collector: keep traces with errors or high latency, drop healthy ones.

💾 Retention

Prometheus 15d, Loki/Tempo 30d on object storage. Use Azure lifecycle management to tier cool/archive.

🔒 Security

Enable RBAC, use Azure AD for Grafana, restrict network policies, enable HTTPS with cert-manager.

SRE interview questions & answers

🎤 Question 1
Use RED metrics: isolate endpoint → exemplar → trace → logs. Confirm root cause (e.g., DB timeout).
🎤 Question 2
Cost: Loki indexes only labels, stores logs in cheap object storage. Elasticsearch indexes full text, expensive to run at scale.
🎤 Question 3
Tempo uses `trace_id` as lookup key in object storage blocks. No indexing of span attributes, making it cheap for high‑volume tracing.
