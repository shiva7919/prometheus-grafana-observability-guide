Observability vs. Monitoring

What’s the difference and why it matters for SREs
📡 Monitoring

What: Collecting predefined metrics and checking against thresholds. Why: To know when something is wrong. Example: CPU > 90% → alert.

🔬 Observability

What: Understanding internal state from external outputs (metrics, logs, traces). Why: To ask unknown questions and debug why something is wrong. Example: Why is the API slow? Explore traces and logs to find the root cause.

🎯 SRE relevance

SREs need both: monitoring for service level indicators (SLIs) and observability for incident investigation. Observability reduces Mean Time To Resolution (MTTR).

Instrumentation – The Key to Observability

What it is, why it’s critical, and how to do it
📝 What is instrumentation?

Instrumentation means adding code to your application to emit telemetry data (metrics, logs, traces). Without instrumentation, you cannot observe your system’s internal behaviour. It’s like adding sensors to a machine – without sensors, you’re blind.

Why it’s critical for SREs: You cannot debug what you cannot measure. Instrumentation must be a first‑class feature, not an afterthought.

📊 Prometheus – Metrics

What, why, architecture, components, and AKS implementation
📖 What is Prometheus?

Open‑source time‑series database and monitoring system. It uses a pull model – it scrapes metrics from HTTP endpoints (exporters).

🎯 Why we need it

Metrics tell you the health of your system – request rate, error rate, latency, resource usage. Without Prometheus, you have no historical view of performance.

📜 Loki – Log Aggregation

What, why, architecture, components, and AKS setup
📖 What is Loki?

Horizontally scalable, cost‑effective log aggregation system inspired by Prometheus. It indexes only labels, not the full log text – making it 10x cheaper than Elasticsearch.

🎯 Why we need it

Logs are essential for debugging. Loki integrates seamlessly with Prometheus labels, so you can correlate metrics and logs using the same metadata (pod, namespace, job).

⏱️ Tempo – Distributed Tracing

What, why, architecture, components, and AKS setup
📖 What is Tempo?

High‑scale distributed tracing backend that stores traces in object storage. It uses TraceID hashing to locate traces – no expensive indexing.

🎯 Why we need it

Traces show the exact path of a request across services. When a request is slow, traces pinpoint the slowest span (e.g., a database query). Essential for microservices.

🏗️ Architecture & Components ⏱️

   │  │(OTLP)    │  │(WAL +    │  │(trace retrieval)│   │
   │  └──────────┘  │  block)  │  └────────┬─────────┘   │

   │                     │                 │             │
   │               ┌─────▼─────┐      ┌────▼─────┐       │
   │               │ ☁️ Azure  │      │  Tempo   │       │
   │               │ Blob      │      │  Query   │       │
   │               │ Storage   │      │  (gRPC)  │       │
   │               └───────────┘      └──────────┘       │

🧰 OpenTelemetry Collector

What, why, architecture, components, and AKS deployment
📖 What is OpenTelemetry Collector?

A vendor‑agnostic agent that receives telemetry data (OTLP), processes it (batch, filter, transform), and exports to multiple backends (Prometheus, Loki, Tempo).

🎯 Why we need it

Decouples instrumentation from backend. You can change backends without modifying application code. Also provides tail‑based sampling, batching, and retries.

🏗️ Architecture & Components 🧰
   ┌─────────────────────────────────────────────────────┐
   │            🧰 OpenTelemetry Collector                │
   │  ┌──────────┐  ┌──────────┐  ┌──────────────────┐   │
   │  │ Receivers│→ │Processors│→ │   Exporters      │   │
   │  │ OTLP,    │  │ batch,   │  │ Prometheus,      │   │
   │  │ Jaeger   │  │ memory   │  │ Loki (OTLP),     │   │
   │  │          │  │          │  │ Tempo (OTLP)     │   │
   │  └──────────┘  └──────────┘  └──────────────────┘   │
   └─────────────────────────────────────────────────────┘
          ▲ OTLP (4317)                │
          │                            ▼
   ┌──────┴──────┐            ┌────────┴────────┐
   │ Instrumented│            │ Backends        │

Components: Receivers (ingest data), Processors (transform/batch), Exporters (send to backends). Can be deployed as an agent (DaemonSet) or gateway (Deployment).

📈 Grafana & Trace‑Log Correlation

Unified UI, datasources, and derived fields
📖 What is Grafana?

Open‑source analytics and visualisation platform. Connects to multiple data sources (Prometheus, Loki, Tempo) and renders dashboards.

🎯 Why we need it

Single pane of glass for metrics, logs, and traces. Correlate a metric spike → logs with TraceID → full trace waterfall – drastically reduces MTTR.

🔗 Trace‑Log correlation (Derived Fields)

When a log line contains a TraceID, Grafana can automatically create a link to the corresponding trace in Tempo. This is the killer feature of the stack.

bash
kubectl get secret -n monitoring kube-prometheus-stack-grafana -o jsonpath="{.data.admin-password}" | base64 -d
kubectl port-forward -n monitoring svc/kube-prometheus-stack-grafana 3000:80

Add data sources in Grafana UI:

  • Loki: URL http://loki-gateway.loki:80 → then add derived field: Name `traceID`, Regex `traceID=(\w+)`, URL `${__value.raw}`, Data source `Tempo`.
  • Tempo: URL http://tempo-query-frontend.tempo:3200
  • Prometheus is pre‑configured.
🔗 Result: Any log line containing `traceID=abc123` becomes a clickable link. Click it → Tempo opens the full trace waterfall.

🐍 Sample instrumented Flask app

Python + OpenTelemetry → traces and logs
python
# app.py – full OpenTelemetry instrumentation
from flask import Flask
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.instrumentation.flask import FlaskInstrumentor
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.sdk.resources import Resource
import logging, time, random

logging.basicConfig(level=logging.INFO, format='{"time": "%(asctime)s", "level": "%(levelname)s", "message": "%(message)s", "traceID": "%(otelTraceId)s"}')
resource = Resource.create(attributes={"service.name": "flask-app"})
trace.set_tracer_provider(TracerProvider(resource=resource))
otlp_exporter = OTLPSpanExporter(endpoint="otel-collector.observability.svc.cluster.local:4317", insecure=True)
trace.get_tracer_provider().add_span_processor(BatchSpanProcessor(otlp_exporter))

app = Flask(__name__)
FlaskInstrumentor().instrument_app(app)

@app.route('/hello')
def hello():
    tracer = trace.get_tracer(__name__)
    with tracer.start_as_current_span("hello-span"):
        time.sleep(random.uniform(0.01, 0.1))
        logging.info("Hello endpoint called", extra={"otelTraceId": trace.get_current_span().get_span_context().trace_id})
        return "Hello, observability!"

@app.route('/slow')
def slow():
    tracer = trace.get_tracer(__name__)
    with tracer.start_as_current_span("slow-span") as span:
        delay = random.uniform(0.5, 2.0)
        span.set_attribute("delay_seconds", delay)
        time.sleep(delay)
        logging.warning("Slow endpoint took %.2f seconds", delay, extra={"otelTraceId": trace.get_current_span().get_span_context().trace_id})
        return f"Waited {delay:.2f}s"

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
