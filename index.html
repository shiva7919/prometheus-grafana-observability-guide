Introduction to Observability

Three pillars, tools landscape, and why Kubernetes changes everything.
📡 Monitoring vs Observability

Monitoring watches known failure modes (CPU > 90%). Observability lets you ask unknown questions using metrics, logs, and traces. Observability is about understanding internal state from external outputs.

🗂️ Three Pillars
  • Metrics – numeric time‑series (Prometheus)
  • Logs – structured/unstructured events (Loki)
  • Traces – request journeys across services (Tempo)
🆚 Bare‑metal vs Kubernetes

Kubernetes introduces ephemeral pods, dynamic service discovery, and high cardinality. Traditional monitoring fails. Prometheus was built for K8s – it auto‑discovers targets, handles short‑lived workloads, and scales with label‑based metrics.

Prometheus – Setting Up Metrics Monitoring

Architecture, Helm install on EKS, and basic dashboards.

Prometheus uses a pull model – it scrapes metrics from HTTP endpoints. In Kubernetes, the kube-prometheus-stack bundles Prometheus, Grafana, Alertmanager, and exporters.

bash
# Add Helm repo and install kube-prometheus-stack
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --set grafana.service.type=LoadBalancer

# Access Grafana (get admin password)
kubectl get secret -n monitoring kube-prometheus-stack-grafana -o jsonpath="{.data.admin-password}" | base64 -d
# Grafana URL: http://<loadbalancer-ip>:80
# Prometheus UI: kubectl port-forward -n monitoring svc/kube-prometheus-stack-prometheus 9090:9090

After installation, explore the default dashboards: Kubernetes / Compute Resources / Cluster. Basic PromQL query: sum(rate(container_cpu_usage_seconds_total[5m])) shows cluster CPU usage.

Instrumentation & Custom Metrics + Alerting

Expose custom metrics, define alert rules, route via Alertmanager.

Using the prom-client library in Node.js (or any Prometheus client), you can expose /metrics with Counter, Gauge, Histogram.

javascript
const express = require('express');
const client = require('prom-client');
const app = express();
const httpRequests = new client.Counter({ name: 'http_requests_total', help: 'Total requests', labelNames: ['method','status'] });
const httpDuration = new client.Histogram({ name: 'http_request_duration_seconds', help: 'Latency', buckets: [0.1,0.5,1,2.5] });
app.get('/api', (req,res) => {
  const end = httpDuration.startTimer();
  httpRequests.inc({ method: 'GET', status: 200 });
  res.json({ ok: true });
  end();
});
app.get('/metrics', async (req,res) => {
  res.set('Content-Type', client.register.contentType);
  res.end(await client.register.metrics());
});
app.listen(3000);

Logging with Loki + Grafana

Lightweight, index‑free logging – deploy Loki and Promtail, query with LogQL.

Loki indexes only labels, not full text – drastically cheaper than Elasticsearch. Use Promtail to tail logs and push to Loki.

bash
# Deploy Loki & Promtail on Kubernetes (simplified)
helm repo add grafana https://grafana.github.io/helm-charts
helm upgrade --install loki grafana/loki-stack --namespace loki --create-namespace \
  --set grafana.enabled=false,promtail.enabled=true,loki.service.type=LoadBalancer

# Add Loki as Grafana datasource: URL http://loki:3100
# LogQL examples:
{namespace="default"} |= "error"
{job="myapp"} | json | level="warn"
rate({app="nginx"} |= "404"[5m])
🔗 Correlate metrics and logs: In Grafana, set up a data link from a Prometheus panel to Loki using the same labels (e.g., pod, namespace).

Distributed Tracing with Tempo

Object‑storage‑based tracing, OTLP ingestion, seamless with Grafana.

Tempo does not index traces – it stores them in block storage (S3, GCS, local) and uses a trace ID to retrieve them. It receives traces via OTLP (gRPC 4317, HTTP 4318).

bash
# Install Tempo with Helm
helm repo add grafana https://grafana.github.io/helm-charts
helm upgrade --install tempo grafana/tempo --namespace tracing --create-namespace \
  --set tempo.receivers.otlp.protocols.grpc.endpoint=0.0.0.0:4317

# Add Tempo datasource in Grafana: URL http://tempo:3200
# Instrument a Python app with OpenTelemetry:
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
tracer = trace.get_tracer("my.service")
span = tracer.start_span("my-operation")
# ... do work ...
span.end()

In Grafana Explore, select Tempo, enter a TraceID, and see the full waterfall. The service graph is automatically generated from trace data.

OpenTelemetry – Unified Observability

Single SDK for metrics, logs, and traces. Export to Prometheus, Loki, Tempo simultaneously.

The OpenTelemetry Collector provides vendor‑agnostic pipelines: receivers → processors → exporters. A single config can send metrics to Prometheus, logs to Loki, traces to Tempo.

OTel Collector Pipeline
Receivers (OTLP, Prometheus, Jaeger) → Processors (batch, memory_limiter) → Exporters (Prometheus, Loki, Tempo)
yaml
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }
processors:
  batch: {}
exporters:
  prometheus: { endpoint: "0.0.0.0:8889" }
  otlphttp/loki: { endpoint: "http://loki:3100/otlp" }
  otlp/tempo: { endpoint: "tempo:4317", tls: { insecure: true } }
service:
  pipelines:
    metrics: { receivers: [otlp], processors: [batch], exporters: [prometheus] }
    logs:    { receivers: [otlp], processors: [batch], exporters: [otlphttp/loki] }
    traces:  { receivers: [otlp], processors: [batch], exporters: [otlp/tempo] }

Golang Microservice Instrumentation

go
import (
  "go.opentelemetry.io/otel"
  "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
  "go.opentelemetry.io/otel/sdk/resource"
  semconv "go.opentelemetry.io/otel/semconv/v1.4.0"
)
func initTracer() {
  exporter, _ := otlptracegrpc.New(ctx, otlptracegrpc.WithInsecure(), otlptracegrpc.WithEndpoint("tempo:4317"))
  tp := sdktrace.NewTracerProvider(sdktrace.WithBatcher(exporter), sdktrace.WithResource(resource.NewWithAttributes(semconv.SchemaURL, semconv.ServiceNameKey.String("my-golang-app"))))
  otel.SetTracerProvider(tp)
}
// Now use tracer = otel.Tracer("my-component") to create spans
✨ End‑to‑end correlation: A single request generates a trace (Tempo), logs containing the TraceID (Loki), and latency metrics (Prometheus). In Grafana, click from a high‑latency metric → view logs for that trace → jump to the trace waterfall.

Top Interview Questions

Loki indexes only labels, not full text – significantly lower storage cost and operational complexity. For cloud‑native environments, Loki integrates seamlessly with Prometheus labels.

Tempo uses object storage (S3, GCS, local) and a hashed TraceID lookup. It does not build an index of trace contents, making it extremely cheap and scalable. Traces are retrieved via exact TraceID.

It decouples instrumentation from backend. You can send OTLP data to the collector, then route to Prometheus (metrics), Loki (logs), Tempo (traces) – or change backends without changing application code.
