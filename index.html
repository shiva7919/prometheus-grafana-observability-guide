Telemetry Engineering, Core Correlation, & Cloud-Native Architecture

An advanced, production-grade handbook for junior SREs and interns. Learn to construct, instrument, secure, operate, and troubleshoot an enterprise observability platform utilizing OpenTelemetry and the Grafana LGTM stack on Azure Kubernetes Service (AKS).

01

Observability vs. Monitoring

Mathematical control theory applied to multi-tenant distributed cloud infrastructure.

In classical operations engineering, Monitoring and Observability are frequently conflated, yet they represent distinct paradigms in systems engineering. Understanding this difference is critical when designing systems capable of operating under five-nines (99.999%) availability requirements.

Defining the Paradigms

📈 Monitoring: The Known-Unknowns

Monitoring is the process of collecting, aggregating, and analyzing a predefined set of metrics to evaluate whether a system is performing within expected boundaries. It addresses known failure modes.

Core Query: "Is the system working according to my static thresholds?"
Mechanism: Synthetics, threshold alerts (e.g., CPU utilization > 85%, HTTP 5xx rate > 1%).

🔬 Observability: The Unknown-Unknowns

Observability is a structural property of a system, derived from Control Theory. A system is observable if its internal states can be fully inferred solely by analyzing its external outputs (telemetry).

Core Query: "Why is this specific, anomalous behavior occurring across a subset of fragmented queries?"
Mechanism: High-cardinality exploratory data analysis, distributed context tracing, cross-pilar ad-hoc correlation.

💡
The SRE Nuance: You cannot purchase observability off the shelf; it must be engineered into the software via runtime instrumentation. Monitoring tells you when a system is breaking; observability equips you to discover why an entirely novel, un-architected failure mode is manifesting in production.

The Three Pillars & Cross‑Pillar Correlation

Mathematical data representations, memory footprints, and structural context injection.

True observability relies on three primary data formats: Metrics, Logs, and Traces. Isolating these datasets leads to institutional silos and prolonged Mean Time to Resolution (MTTR). High-performance SRE teams leverage strict cryptographic and structural cross-linking.

Deep-Dive Data Structural Analysis

Dimension 🔢 Metrics 📄 Logs 🔗 Traces
Mathematical Format Numeric time-series. Composed of an identifier string, label key-value pairs, a numeric value, and an epoch millisecond timestamp. Structured text or unstructured byte array. Optimized when formatted as explicit JSON containing systemic keys. Directed Acyclic Graph (DAG) of spans. Represents structural parent-child executions across process boundaries.
Storage Backend In-memory TSDB with write-ahead logs (WAL) and compressed block chunking (e.g., Prometheus TSDB). Object store containing compressed log stream chunks with index definitions strictly mapped to labels (Loki). High-throughput immutable object block storage indexed exclusively by Trace Identification keys (Tempo).
Cost Profile & Scale O(1) storage scaling relative to application traffic volume. Cost expands linearly with label cardinality. O(N) storage scaling directly proportional to log volume generation and system transaction velocity. High cost profile. O(N) data scaling. Mitigated exclusively through deterministic, adaptive, or head/tail sampling strategies.

Cross-Pillar Correlation Framework

To move instantly across these pillars during an active high-severity incident, you must enforce three strict architectural patterns across all internal services:

  • Trace Context Injection in Logs: Every log entry generated within a transaction execution path must explicitly output the current trace_id and span_id in its structured JSON metadata block.
  • Metric Exemplars: Prometheus metrics must store a reference to a representative trace_id within the TSDB block of a specific bucket observation (e.g., inside histogram latency observations).
  • Unified Labeling (M3 Pattern): Every tool must parse identical key names for the target infrastructure (e.g., k8s.namespace.name, k8s.pod.name, service.name).

Instrumentation Engineering

Injecting sensor pipelines directly into runtime environments.

Instrumentation is the practice of embedding code instructions into an application to emit telemetry. An application without instrumentation is completely opaque, forcing SREs to rely on external inference (e.g., network black-box testing) which fails to reveal internal locks, database connection exhaustion, or memory allocation patterns.

Auto-Instrumentation vs. Manual Instrumentation

Production engineering strategies dictate a two-tiered implementation model:

1. Auto-Instrumentation (The Baselines)

Utilizes runtime bytecode manipulation, monkey-patching, or eBPF hooks to intercept standard framework executions (such as HTTP routing engines, gRPC communication channels, or SQL client drivers). It delivers immediate, out-of-the-box visibility into golden signals without changing codebase lines.

2. Manual Instrumentation (The Business Context)

Requires software engineers to write explicit code utilizing the OpenTelemetry API to track custom business domains. This is essential for capturing granular execution components like loop iterations, domain-specific state states, or specific algorithmic execution boundaries.

💡
Production Rule: Bootstrap every single deployment via standard OpenTelemetry Auto-Instrumentation init-containers. Mandate manual instrumentation only for core domain logic identified in your Tier-1 Service Level Objectives (SLOs).

Grafana Architecture & Visualization

The unified query interface and correlation engine.

Component Breakdown

  • Grafana Core (Go Runtime): High-concurrency backend layer responsible for user authentication, session state persistency, dashboard schema storage (JSON specifications), and reverse-proxying client HTTP telemetry requests.
  • Data Source Plugins: Decoupled, stateless protocol translators running inside Grafana. They take standard query structures from the UI, translate them into target network payloads (PromQL, LogQL, TraceQL), execute them over HTTP/gRPC, and return standardized dataframes.
  • Unified Alerting Engine: Evaluates configured panel rules against downstream databases on a continuous tick scheduler, pushing events directly to target Alertmanagers.

Production Correlation Configuration (Derived Fields)

To enable seamless jumping from Loki logs to Tempo traces with zero manual search operations, configure your Grafana Loki Datasource using the following configuration chunk. This instructs the UI to match trace IDs using regex and format them into interactive hyperlinks:

Prometheus Engine & PromQL

Time-series data architecture, scratch storage blocks, and analytical evaluation.

Architectural Component Deep-Dive

  • Discovery Manager: Continuously polls the Kubernetes API server for updates to Pods, Nodes, and Services. It dynamically recreates scrape targets based on internal metadata annotations without requiring configuration reloads.
  • Scrape Manager: Executes scheduled asynchronous single-concurrency HTTP GET requests against targets using the application/openmetrics-text standard wire protocol.
  • TSDB Engine: Ingested memory metrics are written to an active memory structure called a Head Block, while appending to a sequential disk Write-Ahead Log (WAL) to survive node restarts. Every 2 hours, the Head Block is frozen and cut into a permanent, immutable block directory containing metadata, an inverted index file, and compressed raw sample chunks (using Gorilla XOR delta-of-delta compression).
  • Query Engine: Parses PromQL expressions, maps targets across the block hierarchy, pulls raw byte streams, inflates the values, and performs structural vector transformations.

Advanced PromQL Enterprise Production Patterns

Counter Rate Quantifications (Always apply rate before sum):

promql
sum by (k8s_pod_name) (rate(http_requests_total{status_code=~"5.*"}[5m]))

Histogram Quantile Target Aggregation (95th Percentile Latency Calculation):

promql
histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

Alertmanager Architecture

Deduplication pipelines, inhibitory maps, and routing DAG topologies.

Alertmanager is responsible for processing alert payloads sent by Prometheus. It decouples the alerting engine from notification delivery, preventing alert fatigue during major infrastructure outages.

The Notification Processing Pipeline

  1. Ingestion API: Receives raw HTTP POST payloads containing alert descriptions and context labels from Prometheus.
  2. Grouping Stage: Combines incoming single alerts into grouped notification arrays based on matching configuration boundaries (e.g., grouping 50 distinct container crash loops into a single cluster/namespace alert notification).
  3. Inhibition Processing: Suppresses specific notification classes if another highly critical, blocking root alert is already active (e.g., if NodeNetworkDown triggers, suppress all downstream TargetPodHttpEgressFailing alerts).
  4. Silence Matching: Cross-references incoming alerts against a dynamic in-memory regex map of active maintenance windows, muting matches.
  5. Routing Node Evaluation: Evaluates a routing Directed Acyclic Graph (DAG) to determine the exact end receivers (such as Slack or PagerDuty).

Loki Logs Indexing Architecture

Zero full-text indexing mechanics, storage layouts, and hyper-parallel LogQL streams.

Component Breakdown

  • Distributor: The stateless entry layer that validates incoming log streams, ensures compliance with configured tenancy limits, and hashes metadata labels to route streams to correct Ingesters.
  • Ingester: Holds open log chunks in volatile memory, batching lines into compressed block formats. When blocks reach capacity parameters (e.g., 2 hours or 4MB), they flush them directly to Azure Blob Storage.
  • Querier / Query Frontend: Receives complex LogQL parameters, breaks large time-range queries into highly parallel sub-tasks, distributes execution across workers, and aggregates results.

Production LogQL Query Patterns

High-Capacity JSON Attribute Traversal:

logql
{namespace="production", app="api-gateway"} | json | status_code >= 500 |= "database connection timeout"

Dynamic Log Metricization (Error Velocity Computations):

logql
sum by (path) (rate({namespace="production"} | json | level="error" [5m]))

Tempo Distributed Tracing Architecture

Massive ID-only block indices and object store lookup acceleration.

System Processing Components

  • Distributor: Ingests distributed span segments via OTLP over gRPC. It validates span payload structures and loads balancing routines across the internal cluster.
  • Ingester: Constructs trace blocks in memory by linking disjointed span streams using their shared 128-bit trace_id. It flushes these blocks once they hit structural limits.
  • Compactor: Asynchronously pulls raw small blocks from object storage, groups them into larger, optimized blocks, and strips out duplicate metadata to keep lookups fast.
  • Querier: Finds trace arrays based on strict ID mappings. It uses bloom filters to quickly scan block indexes without downloading large binary blobs from Azure storage.

OpenTelemetry Collector Architecture

Vendor-agnostic proxy pipelines, transformation processing, and batching mechanisms.

Data Flow Pipeline Breakdown

  • Receivers: The ingress protocol ports for the collector. They support multiple industry formats (such as native OTLP, zipkin, or prometheus scraping) and translate them into an internal, unified memory model.
  • Processors: The computational core. They perform critical operations like batching network queries, scrubbing sensitive user data (PII) using regex, managing local memory limits, and dropping noisy traces.
  • Exporters: The translation output layers. They map internal data back into native target vendor formats (Prometheus, Loki, Tempo, or Datadog) and push them out over the network.

Production OpenTelemetry Collector Configuration Spec

yaml

        spike_limit_percentage: 15
      batch:
        send_batch_size: 8192

        send_batch_max_size: 10240
      resourcedetection:
        detectors: [env, azure]
        timeout: 2s

    exporters:
      prometheus:
        endpoint: "0.0.0.0:8889"

          exporters: [otlp/tempo]
      telemetry:
        logs:
          level: "info"

AKS Prerequisites & Workload Identity

Securing infrastructure using passwordless Entra ID integrations.

Using raw storage account keys inside your Kubernetes cluster creates security risks if secrets are leaked. To eliminate static credentials, we implement **Azure Workload Identity**. This approach establishes token federation between Azure Entra ID and Kubernetes ServiceAccounts.

Step-by-Step Enterprise Provisioning Pipeline

bash
# Declare target configurations
export RG_NAME="observability-prod-rg"
export LOCATION="eastus"
export CLUSTER_NAME="aks-core-prod"
export IDENTITY_NAME="loki-storage-pod-identity"

# 1. Create Resource Group and AKS Cluster with explicit OIDC/Workload Identity features
az group create --name $RG_NAME --location $LOCATION

az aks create --resource-group $RG_NAME --name $CLUSTER_NAME \
  --node-count 3 --enable-oidc-issuer --enable-workload-identity \
  --generate-ssh-keys --network-plugin azure

# Retrieve credentials context
az aks get-credentials --resource-group $RG_NAME --name $CLUSTER_NAME

# Extract cluster OIDC URL mapping for structural trust federation
export AKS_OIDC_ISSUER="$(az aks show --resource-group $RG_NAME --name $CLUSTER_NAME --query oidcIssuerProfile.issuerUrl -o tsv)"

# 2. Provision Managed Identity inside Azure Entra ID
az identity create --name $IDENTITY_NAME --resource-group $RG_NAME
export USER_ASSIGNED_CLIENT_ID="$(az identity show --name $IDENTITY_NAME --resource-group $RG_NAME --query clientId -o tsv)"
export USER_ASSIGNED_PRINCIPAL_ID="$(az identity show --name $IDENTITY_NAME --resource-group $RG_NAME --query principalId -o tsv)"

# 3. Grant RBAC Permissions to Managed Identity over Object Storage
export STORAGE_ID="$(az storage account show --name srelokichunks2026 --resource-group myRG --query id -o tsv)"
az role assignment create --role "Storage Blob Data Contributor" \
  --assignee $USER_ASSIGNED_PRINCIPAL_ID --scope $STORAGE_ID

# 4. Create Kubernetes Target Namespaces
kubectl create namespace loki

# 5. Build trust relation by creating a Federated Identity Credential
az identity federated-credential create --name "loki-federated-trust" \
  --identity-name $IDENTITY_NAME --resource-group $RG_NAME \
  --issuer "$AKS_OIDC_ISSUER" \
  --subject "system:serviceaccount:loki:loki-sa"

# 6. Build Target ServiceAccount containing explicit Cloud Registration Annotations
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: loki-sa
  namespace: loki
  annotations:
    azure.workload.identity/client-id: "${USER_ASSIGNED_CLIENT_ID}"
EOF

Instrumented Python Application

Production manual instrumentation, structured log generation, and Kubernetes manifests.

The code blocks below show how to build an application using the official OpenTelemetry API. This setup generates metrics, logs, and distributed trace contexts while propagating trace data downstream.

Production Instrumented Application Engine

python
import time
import logging
import json
from flask import Flask, request, jsonify
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource
from opentelemetry.metrics import get_meter_provider, set_meter_provider
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.sdk.metrics.export import PeriodicExportingMetricReader
from opentelemetry.exporter.otlp.proto.grpc.metric_exporter import OTLPMetricExporter

# 1. Initialize Core Infrastructure Resource Metrics
resource = Resource.create(attributes={"service.name": "payment-processor", "environment": "production"})

# 2. Setup Distributed Tracing Infrastructure
provider = TracerProvider(resource=resource)
processor = BatchSpanProcessor(OTLPSpanExporter(endpoint="otel-collector.monitoring.svc.cluster.local:4317", insecure=True))
provider.add_span_processor(processor)
trace.set_tracer_provider(provider)
tracer = trace.get_tracer(__name__)

# 3. Setup Metrics Engine
reader = PeriodicExportingMetricReader(OTLPMetricExporter(endpoint="otel-collector.monitoring.svc.cluster.local:4317", insecure=True))
meter_provider = MeterProvider(resource=resource, metric_readers=[reader])
set_meter_provider(meter_provider)
meter = get_meter_provider().get_meter(__name__)
http_transaction_counter = meter.create_counter("payment_processed_total", description="Total processed payments count")

# 4. Configure Structured JSON Logging Mechanism
class StructuredJsonFormatter(logging.Formatter):
    def format(self, record):
        current_span = trace.get_current_span()
        context = current_span.get_span_context()
        log_payload = {
            "timestamp": self.formatTime(record, self.datefmt),
            "level": record.levelname,
            "message": record.getMessage(),
            "logger": record.name
        }
        if context.is_valid:
            log_payload["trace_id"] = hex(context.trace_id)[2:]
            log_payload["span_id"] = hex(context.span_id)[2:]
        return json.dumps(log_payload)

log_handler = logging.StreamHandler()
log_handler.setFormatter(StructuredJsonFormatter())
logger = logging.getLogger("ProductionApp")
logger.setLevel(logging.INFO)
logger.addHandler(log_handler)

# 5. Initialize Flask Framework
app = Flask(__name__)

@app.route("/process-payment", methods=["POST"])
def process_payment():
    with tracer.start_as_current_span("ExecutePaymentTransaction") as active_span:
        payload = request.get_json() or {}
        user_id = payload.get("user_id", "unknown")
        amount = payload.get("amount", 0.0)
        
        active_span.set_attribute("payment.user_id", user_id)
        active_span.set_attribute("payment.amount", amount)
        
        logger.info(f"Initiating financial validation sequence for transaction route user: {user_id}")
        
        if amount <= 0:
            active_span.set_status(trace.Status(trace.StatusCode.ERROR, "Invalid Transaction Amount Parameters"))
            logger.error("Payment execution halted due to anomalous pricing vectors.")
            return jsonify({"status": "failed", "error": "Invalid Amount"}), 400
            
        time.sleep(0.12) # Simulating execution latency
        http_transaction_counter.add(1, {"status": "success"})
        logger.info("Payment authentication validated completely.")
        return jsonify({"status": "success", "transaction_id": "tx_992182"}), 200

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8080)

Incident Correlative Workflow

How to navigate an operational incident using data correlation.

When an production outage occurs, relying on ad-hoc queries lengthens your Mean Time to Resolution (MTTR). Follow this structured incident mitigation playbook using cross-pillar data linking:

Step-by-Step Incident Investigation Playbook

Step 1: The Outage Alert Trigger

An Alertmanager notification alerts the on-call SRE engineer via PagerDuty: HTTP 5xx Spike Detected on payment-processor service. The message includes an embedded link to the target Grafana SLA Dashboard.

Step 2: Metric Evaluation & Exemplar Discovery

The engineer opens the Grafana dashboard. In the latency histogram chart, they hover over the elevated 500 error plots. Thanks to configured Exemplars, specific data points expose a clear, hyperlinked trace key context: trace_id=4a20b98a3e712f00.

Step 3: Distributed Trace Inspection

Clicking the exemplar link opens a side-by-side view in Tempo. The trace visualization maps the request's journey across the system architecture: IngressGateway → API-Server → Payment-Processor → DatabaseClient. The span timeline shows that DatabaseClient is taking 12.4 seconds before failing with an error state.

Step 4: Targeted Log Aggregation Lookup

Using the **Derived Fields** link embedded inside the Tempo panel, the engineer clicks "View Logs for this Trace". Grafana queries Loki for that exact trace ID across the system. Loki pulls up the matching logs, revealing the precise error signature: {"trace_id": "4a20b98a3e712f00", "level": "CRITICAL", "message": "PostgreSQL connection pool exhausted. Active leaks detected in database-pool driver."}.

Step 5: Root Cause Remediation

The engineer identifies the root cause: connection pool exhaustion caused by un-reclaimed connections in a recent code change. They safely roll back the deployment to version `v1.0.3` using their GitOps pipeline, clearing the incident.

Best Practices & Cost Controls

Controlling telemetry ingestion volume and managing cardinality explosions.

Uncontrolled telemetry data ingestion can quickly become a major infrastructure expense. SRE teams use strict data hygiene rules to prevent cost increases.

Managing Metric Cardinality

Metric cardinality is defined as the total number of unique time-series combinations, calculated as the product of all label values. Avoid assigning high-uniqueness variables (like raw user IDs, session tokens, or IP addresses) as Prometheus labels.

Cardinality Equation: Total Series = (Metrics) × (Versions) × (Pods) × (User IDs). Adding 100,000 distinct user IDs to a metric creates 100,000 unique series, which can cause Prometheus to crash with Out-Of-Memory (OOM) errors.

Advanced Sampling Techniques

  • Head-Based Sampling: The sampling decision is made at the start of a transaction (e.g., sample exactly 5% of all incoming requests). This approach is simple to implement but risks dropping rare error traces.
  • Tail-Based Sampling: The OpenTelemetry Collector buffers all trace spans in memory until a transaction completes. It then evaluates the full execution pathway. If the transaction encountered an error or high latency, it saves 100% of the trace; if successful, it drops it. This prevents storage bloat while retaining high-value data.

SRE Interview Board Preparation

Core architectural questions commonly used in technical screening loops.
Technical Screening Questions

Scraping gaps typically point to one of three root causes:

  • Target Scraping Failures: The application runtime is experiencing thread starvation or lock contention, preventing it from serving the `/metrics` endpoint within the configured timeout window.
  • Network Delays: Network congestion or strict network security rules are dropping packets between Prometheus and the target application pods.
  • Prometheus Storage Saturation: The Prometheus engine is falling behind on writing to its disk arrays, causing its ingestion loop to stall. REMEDIATION: Review the internal Prometheus metric `prometheus_target_scrapes_sample_limit_hit_total`, increase the scrape timeout configurations, or split your infrastructure into separate Prometheus functional shards.

Trace Context Propagation ensures that unique execution identifiers travel with a request as it crosses process and network boundaries. When an application makes an external network call, the OpenTelemetry SDK injects specific metadata headers—most commonly following the W3C Trace Context standard—into the outbound request payload:

  • traceparent: Composes versioning information, a unified 128-bit Trace ID, a unique 64-bit Parent Span ID, and execution sampling flags.
  • tracestate: Passes key-value pairs used to route traffic or include vendor-specific tracking information.

When the downstream service receives the request, its internal middleware extracts these headers and sets them as the parent context for any new child spans it creates.
