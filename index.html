Observability – why it matters

What is it? Why do we need it? Where is it used?
🔍 What is observability?

The ability to understand the internal state of a system by looking at its external outputs (metrics, logs, traces). Not just monitoring – it lets you ask unknown questions about failures.

🎯 Why SREs need it

To reduce Mean Time To Detection (MTTD) and Mean Time To Resolution (MTTR). Observability helps you pinpoint the root cause of a slowdown or outage without guessing.

🏢 Where used

Every production Kubernetes cluster, microservices architecture, and cloud environment. Essential for incident response, capacity planning, and performance tuning.

💡 Key takeaway: Observability is a design property – you must instrument your code and infrastructure from the beginning.

Prometheus – Metrics

What, why, where, and how to implement on AKS

What it is: Open‑source time‑series database and monitoring system. Pulls metrics from targets (pods, nodes, services) and stores them as labelled data points.
Why needed: Metrics tell you the health of your system – CPU, memory, request rate, error count. Without metrics, you're flying blind.
Where used: Inside every Kubernetes cluster, often as the primary data source for dashboards and alerts.

bash
# Install kube-prometheus-stack on AKS (full monitoring suite)
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --set grafana.service.type=LoadBalancer \
  --set prometheus.prometheusSpec.storageSpec.volumeClaimTemplate.spec.storageClassName=managed-premium \
  --set prometheus.prometheusSpec.retention=15d

How to delete:

bash
helm uninstall kube-prometheus-stack -n monitoring
kubectl delete ns monitoring

Loki – Log Aggregation

What, why, where, and how to set up with Azure Blob Storage

What it is: Horizontally scalable, cost‑effective log aggregation system inspired by Prometheus. It indexes only metadata (labels), not the full log text.
Why needed: Logs are essential for debugging. Traditional systems (Elasticsearch) become expensive at scale. Loki reduces storage cost by ~10x.
Where used: Alongside Prometheus in the same cluster; logs are stored in object storage (Azure Blob).

📌 For AKS: Loki needs Azure Blob Storage for chunks. Create a storage account and container before installing.
bash
# Add Grafana Helm repo
helm repo add grafana https://grafana.github.io/helm-charts
# Install Loki in simple scalable mode with Azure backend
helm upgrade --install loki grafana/loki \
  --namespace loki --create-namespace \
  --set loki.storage.type=azure \
  --set loki.storage.azure.accountName=YOUR_STORAGE_ACCOUNT \
  --set loki.storage.azure.useManagedIdentity=true \
  --set loki.storage.azure.containerName=loki-chunks

Delete Loki:

bash
helm uninstall loki -n loki
kubectl delete ns loki

Tempo – Distributed Tracing

What, why, where, and how to implement with Azure Blob

What it is: High‑scale distributed tracing backend that stores traces in object storage. Uses TraceID to retrieve full request journeys.
Why needed: Traces show you the exact path of a request across services. When a request is slow, traces pinpoint the slowest span (e.g., a database query).
Where used: In microservices architectures, especially when you have more than 3 services.

bash
# Install Tempo with Azure Blob storage backend
helm upgrade --install tempo grafana/tempo \
  --namespace tempo --create-namespace \
  --set tempo.config.storage.trace.backend=azure \
  --set tempo.config.storage.trace.azure.container_name=tempo-data \
  --set tempo.config.storage.trace.azure.account_name=YOUR_STORAGE_ACCOUNT \
  --set tempo.config.storage.trace.azure.use_managed_identity=true

Delete:

bash
helm uninstall tempo -n tempo
kubectl delete ns tempo

OpenTelemetry – Unified Instrumentation

What, why, where, and how to configure the collector

What it is: A single, vendor‑agnostic set of APIs, SDKs, and tools to generate and collect telemetry data (metrics, logs, traces).
Why needed: Instead of using separate libraries for Prometheus (metrics), Loki (logs), and Tempo (traces), OTel gives you one way to instrument your code and forward data to any backend.
Where used: In application code (Python, Go, Java, Node.js) and as a collector sidecar/gateway in the cluster.

yaml
# OTel Collector configuration (configmap)
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }
processors:
  batch: {}
exporters:
  prometheus: { endpoint: "0.0.0.0:8889" }
  otlphttp/loki: { endpoint: "http://loki.loki.svc.cluster.local:3100/otlp" }
  otlp/tempo: { endpoint: "tempo.tempo.svc.cluster.local:4317", tls: { insecure: true } }
service:
  pipelines:
    metrics: { receivers: [otlp], processors: [batch], exporters: [prometheus] }
    logs:    { receivers: [otlp], processors: [batch], exporters: [otlphttp/loki] }
    traces:  { receivers: [otlp], processors: [batch], exporters: [otlp/tempo] }

Delete Collector: kubectl delete deployment otel-collector -n observability

Grafana & Alertmanager

Unified dashboards, alert rules, and silences

Grafana visualises metrics, logs, and traces in one place. Alertmanager handles alert deduplication, grouping, and routing (Slack, PagerDuty, email). After deploying the stack, add data sources:

  • Prometheus: http://kube-prometheus-stack-prometheus.monitoring:9090
  • Loki: http://loki-gateway.loki:80
  • Tempo: http://tempo-query-frontend.tempo:3200
🔗 Correlation: Configure derived fields in Loki to extract TraceID and link directly to Tempo traces.

Deploy the complete stack on AKS

Step‑by‑step from zero to running
📋 Prerequisites
  • Azure CLI, kubectl, Helm installed
  • An Azure subscription
  • Workload identity enabled on AKS (for Blob access)
🏗️ Create AKS cluster
az aks create -g myRG -n observability-cluster --node-count 2 --enable-workload-identity --generate-ssh-keys
az aks get-credentials -g myRG -n observability-cluster
🧪 Deploy all components

Follow the installation commands in sections 2–6. The order does not matter, but install Prometheus first so Grafana is ready.

🧪 Lab 1: Instrument a sample app
Deploy a simple Python Flask app with OpenTelemetry auto‑instrumentation. Send traces to Tempo and logs to Loki. Then generate load and watch the unified Grafana dashboard.

Cleanup & Delete Everything

Remove resources to avoid costs
bash
# 1. Uninstall Helm releases
helm uninstall kube-prometheus-stack -n monitoring
helm uninstall loki -n loki
helm uninstall tempo -n tempo
# 2. Delete namespaces
kubectl delete ns monitoring loki tempo
# 3. Delete AKS cluster
az aks delete -g myRG -n observability-cluster --yes
# 4. Delete Azure Blob storage accounts (optional)
az storage account delete -n mystorageaccount -g myRG --yes
💰 Always verify that no PVCs or external resources are left behind. Check Azure Portal for lingering disks.

Hands‑on labs for interns

Learn by doing – realistic failure scenarios
🎓 Lab 1: Metric spike investigation
1. Deploy a sample nginx pod. 2. Generate CPU load: kubectl exec -it nginx -- bash -c "stress --cpu 2". 3. Open Grafana → Prometheus → query rate(container_cpu_usage_seconds_total[5m]). 4. Observe spike. 5. Identify the pod label, correlate with logs from Loki.
🎓 Lab 2: Trace a slow request
1. Deploy a two‑service app (frontend + backend). 2. Instrument both with OTel. 3. Add artificial sleep in the backend. 4. Call the endpoint. 5. In Grafana → Tempo → search for traces with latency > 1s. 6. Inspect the span that consumes the most time.
🎓 Lab 3: SLO error budget alert
1. Create a Prometheus alert rule that fires when error rate > 5% for 2 minutes. 2. Use a load generator to produce 10% 500 errors. 3. Check Alertmanager UI (port 9093) and see the alert state change from PENDING to FIRING. 4. Configure a Slack webhook and verify notification.
🧪 Final project (week‑long): Set up the full AKS stack, instrument a real microservices demo (e.g., Online Boutique by Google), and build a Grafana dashboard that shows RED (Rate, Errors, Duration) for each service, plus a logs panel that filters errors, and a trace panel that links from slow requests.
