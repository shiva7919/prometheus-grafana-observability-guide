Observability – why it matters

What is it? Why do we need it? Where is it used?
🔍 What is observability?

The ability to understand the internal state of a system by looking at its external outputs (metrics, logs, traces). Not just monitoring – it lets you ask unknown questions about failures.

🎯 Why SREs need it

To reduce Mean Time To Detection (MTTD) and Mean Time To Resolution (MTTR). Observability helps you pinpoint the root cause of a slowdown or outage without guessing.

🏢 Where used

Every production Kubernetes cluster, microservices architecture, and cloud environment. Essential for incident response, capacity planning, and performance tuning.

💡 Key takeaway: Observability is a design property – you must instrument your code and infrastructure from the beginning.

Prometheus – Metrics

What, why, where, and how to implement on AKS

What it is: Open‑source time‑series database and monitoring system. Pulls metrics from targets (pods, nodes, services) and stores them as labelled data points.
Why needed: Metrics tell you the health of your system – CPU, memory, request rate, error count. Without metrics, you're flying blind.
Where used: Inside every Kubernetes cluster, often as the primary data source for dashboards and alerts.

bash
# Add Helm repo and install kube-prometheus-stack
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --set grafana.service.type=LoadBalancer \
  --set prometheus.prometheusSpec.storageSpec.volumeClaimTemplate.spec.storageClassName=managed-premium \
  --set prometheus.prometheusSpec.retention=15d

How to delete:

bash
helm uninstall kube-prometheus-stack -n monitoring
kubectl delete ns monitoring

Loki + Promtail – Log Aggregation

What, why, where, and how to set up with Azure Blob Storage and log collection

What it is: Horizontally scalable, cost‑effective log aggregation system inspired by Prometheus. It indexes only metadata (labels), not the full log text.
Why needed: Logs are essential for debugging. Traditional systems (Elasticsearch) become expensive at scale. Loki reduces storage cost by ~10x.
Where used: Alongside Prometheus in the same cluster; logs are stored in object storage (Azure Blob).

📌 For AKS: Loki needs Azure Blob Storage for chunks. Create a storage account and container before installing.
bash
# Create storage account and container (run once)
az storage account create -n mystorageaccount -g myRG --sku Standard_LRS --kind StorageV2
az storage container create --name loki-chunks --account-name mystorageaccount --auth-mode login

# Install Loki with Promtail enabled (logs collection)
helm repo add grafana https://grafana.github.io/helm-charts
helm upgrade --install loki grafana/loki-stack \
  --namespace loki --create-namespace \
  --set loki.storage.type=azure \
  --set loki.storage.azure.accountName=mystorageaccount \
  --set loki.storage.azure.useManagedIdentity=true \
  --set loki.storage.azure.containerName=loki-chunks \
  --set promtail.enabled=true \
  --set promtail.config.lokiAddress="http://loki-gateway.loki.svc.cluster.local:80"

Delete Loki & Promtail:

bash
helm uninstall loki -n loki
kubectl delete ns loki

Tempo – Distributed Tracing

What, why, where, and how to implement with Azure Blob

What it is: High‑scale distributed tracing backend that stores traces in object storage. Uses TraceID to retrieve full request journeys.
Why needed: Traces show you the exact path of a request across services. When a request is slow, traces pinpoint the slowest span (e.g., a database query).
Where used: In microservices architectures, especially when you have more than 3 services.

bash
# Create storage container for Tempo
az storage container create --name tempo-data --account-name mystorageaccount --auth-mode login

# Install Tempo with Azure Blob storage backend
helm upgrade --install tempo grafana/tempo \
  --namespace tempo --create-namespace \
  --set tempo.config.storage.trace.backend=azure \
  --set tempo.config.storage.trace.azure.container_name=tempo-data \
  --set tempo.config.storage.trace.azure.account_name=mystorageaccount \
  --set tempo.config.storage.trace.azure.use_managed_identity=true

Delete:

bash
helm uninstall tempo -n tempo
kubectl delete ns tempo

Grafana Dashboards & Correlation

Unified UI, data sources, and TraceID‑log linking

After installing kube-prometheus-stack, Grafana is already running. Expose it and add the missing data sources.

bash
# Get Grafana admin password
kubectl get secret -n monitoring kube-prometheus-stack-grafana -o jsonpath="{.data.admin-password}" | base64 -d
# Port‑forward for local access (or use LoadBalancer IP)
kubectl port-forward -n monitoring svc/kube-prometheus-stack-grafana 3000:80

Add Loki & Tempo datasources via Grafana UI:

  • Configuration → Data sources → Add data source → Loki → URL: http://loki-gateway.loki:80 → Save & Test
  • Add Tempo → URL: http://tempo-query-frontend.tempo:3200 → Save & Test
🔗 TraceID‑Log correlation (derived fields): In Loki datasource settings, add a derived field:
Name: traceID, Regex: traceID=(\w+), URL: ${__value.raw}, Data source: Tempo (UID). This turns every log line containing a TraceID into a clickable link to the trace.

AKS Prerequisites & Workload Identity

Azure setup, managed identities, and storage roles
⚠️ Cost warning: AKS cluster, storage accounts, and managed identities incur costs. Delete everything after the lab to avoid unexpected charges.
bash
# 1. Login to Azure
az login
az account set --subscription "your-subscription-id"

# 2. Create resource group
az group create --name myRG --location eastus

# 3. Create AKS cluster with workload identity enabled
az aks create -g myRG -n observability-cluster --node-count 2 --enable-workload-identity --generate-ssh-keys
az aks get-credentials -g myRG -n observability-cluster

# 4. Create user-assigned managed identity for Loki & Tempo
az identity create -g myRG -n loki-storage-id
az identity create -g myRG -n tempo-storage-id

# 5. Assign Storage Blob Data Contributor role to each identity on the storage account
STORAGE_ACCOUNT_ID=$(az storage account show -n mystorageaccount -g myRG --query id -o tsv)
az role assignment create --assignee $(az identity show -g myRG -n loki-storage-id --query principalId -o tsv) \
  --role "Storage Blob Data Contributor" --scope $STORAGE_ACCOUNT_ID
az role assignment create --assignee $(az identity show -g myRG -n tempo-storage-id --query principalId -o tsv) \
  --role "Storage Blob Data Contributor" --scope $STORAGE_ACCOUNT_ID

# 6. Federate Kubernetes service accounts to Azure identities
export OIDC_ISSUER_URL="$(az aks show -g myRG -n observability-cluster --query oidcIssuerProfile.issuerUrl -o tsv)"
# For Loki
az identity federated-credential create --name loki-federated --identity-name loki-storage-id -g myRG \
  --issuer $OIDC_ISSUER_URL --subject system:serviceaccount:loki:loki
# For Tempo
az identity federated-credential create --name tempo-federated --identity-name tempo-storage-id -g myRG \
  --issuer $OIDC_ISSUER_URL --subject system:serviceaccount:tempo:tempo

# 7. Annotate the service accounts (run after installing Loki/Tempo)
kubectl annotate serviceaccount -n loki loki azure.workload.identity/client-id=$(az identity show -g myRG -n loki-storage-id --query clientId -o tsv)
kubectl annotate serviceaccount -n tempo tempo azure.workload.identity/client-id=$(az identity show -g myRG -n tempo-storage-id --query clientId -o tsv)

Sample instrumented Flask app

Python + OpenTelemetry – sends traces to Tempo and logs to Loki
python
# app.py
from flask import Flask
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.instrumentation.flask import FlaskInstrumentor
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.sdk.resources import Resource
import logging, time, random

# Configure logging to JSON (Loki likes structured logs)
logging.basicConfig(level=logging.INFO, format='{"time": "%(asctime)s", "level": "%(levelname)s", "message": "%(message)s", "traceID": "%(otelTraceId)s"}')

resource = Resource.create(attributes={"service.name": "flask-app"})
trace.set_tracer_provider(TracerProvider(resource=resource))
otlp_exporter = OTLPSpanExporter(endpoint="otel-collector.observability.svc.cluster.local:4317", insecure=True)
trace.get_tracer_provider().add_span_processor(BatchSpanProcessor(otlp_exporter))

app = Flask(__name__)
FlaskInstrumentor().instrument_app(app)

@app.route('/hello')
def hello():
    tracer = trace.get_tracer(__name__)
    with tracer.start_as_current_span("hello-span"):
        time.sleep(random.uniform(0.01, 0.1))
        logging.info("Hello endpoint called", extra={"otelTraceId": trace.get_current_span().get_span_context().trace_id})
        return "Hello, observability!"

@app.route('/slow')
def slow():
    tracer = trace.get_tracer(__name__)
    with tracer.start_as_current_span("slow-span") as span:
        delay = random.uniform(0.5, 2.0)
        span.set_attribute("delay_seconds", delay)
        time.sleep(delay)
        logging.warning("Slow endpoint took %.2f seconds", delay, extra={"otelTraceId": trace.get_current_span().get_span_context().trace_id})
        return f"Waited {delay:.2f}s"

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)

Dockerfile and Kubernetes deployment:

dockerfile
FROM python:3.10-slim
WORKDIR /app
RUN pip install flask opentelemetry-distro opentelemetry-exporter-otlp
RUN opentelemetry-bootstrap -a install
COPY app.py .
CMD ["opentelemetry-instrument", "python", "app.py"]

  - port: 5000
    targetPort: 5000

Delete sample app: kubectl delete -f deployment.yaml

🧪 Test correlation: Generate load: kubectl run load-generator --image=curlimages/curl --rm -it -- /bin/sh -c "while true; do curl http://flask-app:5000/slow; sleep 1; done". In Grafana, find a slow trace, click the trace ID, and see the correlated log line.

Complete cleanup – avoid costs

Remove every resource created

bash
# 1. Uninstall Helm releases
helm uninstall kube-prometheus-stack -n monitoring
helm uninstall loki -n loki
helm uninstall tempo -n tempo
helm uninstall otel-collector -n observability

# 2. Delete namespaces
kubectl delete ns monitoring loki tempo observability

# 3. Delete the AKS cluster
az aks delete -g myRG -n observability-cluster --yes

# 4. Delete storage account (and all containers)
az storage account delete -n mystorageaccount -g myRG --yes

# 5. Delete managed identities
az identity delete -g myRG -n loki-storage-id
az identity delete -g myRG -n tempo-storage-id

# 6. Delete resource group (optional, deletes everything at once)
az group delete -n myRG --yes --no-wait

Hands‑on labs for interns

Learn by doing – realistic failure scenarios
🎓 Lab 1: Metric spike investigation
1. Deploy a sample nginx pod: kubectl run nginx --image=nginx. 2. Generate CPU load: kubectl exec -it nginx -- bash -c "apt update && apt install -y stress && stress --cpu 2". 3. In Grafana, query rate(container_cpu_usage_seconds_total{pod="nginx"}[5m]). 4. Observe spike. 5. Correlate with logs from Loki (Promtail collects container logs).
🎓 Lab 2: Trace a slow request
1. Deploy the Flask app above. 2. Generate load to /slow with hey -z 30s -c 5 http://flask-app/slow. 3. In Grafana Explore → Tempo → search for traces with latency > 1s. 4. Click a trace – identify the span slow-span. 5. Use the derived field to open the corresponding Loki log.
🎓 Lab 3: SLO error budget alert
1. Create a PrometheusRule: cat <<EOF | kubectl apply -f - (prometheusrule yaml). 2. Use a load generator that returns HTTP 500 for 10% of requests. 3. Watch Alertmanager UI at port 9093. 4. Configure Slack webhook (optional).
