Observability vs. Monitoring

Detailed definitions and why observability is a system property
📡 Monitoring

Collecting predefined metrics and checking against thresholds. It answers "Is something wrong?" Example: CPU > 90% → alert.

🔬 Observability

Understanding internal state from external outputs (metrics, logs, traces). It lets you ask unknown questions during an incident. Example: "Why is the API slow?" – explore traces and logs to find root cause.

In control theory, a system is observable if its complete internal state can be reconstructed from its outputs. In cloud‑native systems, outputs are telemetry data.

🎯 Why SREs need both

Monitoring for service level indicators (SLIs) and alerting. Observability for incident investigation (reduces MTTR). Without observability, you know that something is broken but not why.

AspectMonitoringObservability Data cardinalityLow (aggregated CPU, memory)High (user ID, trace ID, feature flag) Storage orientationTime series with limited labelsEvent‑based with high‑dimensional context Query styleKnown dashboards and fixed alertsExploratory, ad‑hoc, joining data types Debugging capabilityFinds known signatures (e.g., memory leak)Finds unknown causal chains (e.g., A/B test + region + database replica) Tool exampleNagios, ZabbixGrafana + Prometheus + Loki + Tempo
💡 Key nuance: Monitoring is a subset of observability. You still need monitoring for alerting. Observability adds the exploration layer.

The Three Pillars & Cross‑Pillar Correlation

Metrics, logs, traces – data formats, storage, and how they connect
🔢 Metrics

Format: <metric_name>{<label>=<value>} <value> <timestamp>
Storage: Time‑series DB (Prometheus TSDB)
Operations: rate(), increase(), histogram_quantile()
Example: http_requests_total{method="POST",status="500"}

📄 Logs

Format: Structured (JSON) or unstructured text with timestamp and level
Storage: Object storage with index on labels (Loki)
Operations: filtering, regex, aggregation
Example: {"time":"...","level":"error","trace_id":"abc123","msg":"payment failed"}

🔗 Traces

Format: Spans with trace_id, span_id, parent_span_id, duration, attributes
Storage: Object storage with trace ID indexing (Tempo)
Operations: trace retrieval, service graphs
Example span: span name="authenticate" duration=45ms attributes={user_id="123"}

▸ Cross‑pillar correlation workflow
  1. Metric (counter increment) alerts → fire
  2. Exemplar from Prometheus gives trace_id
  3. Tempo shows full trace: auth took 2s (should be 50ms)
  4. Log attached to trace_id shows "token validation failed, retrying"
🔗 Implementation pattern: Inject trace_id into logs. Use trace_id as a label in metrics (sparingly). Use exemplars to jump from metric to trace.

Instrumentation – The Key to Observability

What it is, why critical, and how to do it
📝 What is instrumentation?

Adding code to your application to emit telemetry data (metrics, logs, traces). Without instrumentation, you cannot observe internal behaviour – it's like adding sensors to a machine.

Why critical for SREs: You cannot debug what you cannot measure. Instrumentation must be a first‑class feature, not an afterthought.

▸ Instrumentation types with OpenTelemetry
  🧩 Auto‑instrumentation          ✍️ Manual instrumentation
  (language agent)                     (custom spans/metrics)
           │                                      │
           └──────────────┬───────────────────────┘
                          ▼

                          │

💡 Best practice: Always expose a /metrics endpoint and add trace propagation headers. Start with auto‑instrumentation, then add manual spans for business‑critical operations.

📈 Grafana – Visualization Layer

Architecture, data sources, and unified dashboarding
📖 What is Grafana?

Open‑source analytics and visualisation platform. Connects to multiple data sources (Prometheus, Loki, Tempo, Alertmanager) and renders dashboards.

🏗️ Architecture

Browser (React) → Grafana Server (Go) → Data source plugins → Backend databases
Components: Frontend (React), Backend server (auth, proxy), Plugins (Prometheus, Loki, Tempo), Alerting engine.

🔗 Data flow for a dashboard

1. User selects time range and variable → 2. Grafana sends parameterised PromQL to Prometheus → 3. Prometheus returns time series → 4. Grafana renders chart → 5. User clicks data point → exemplar → opens Tempo trace → 6. From trace, click "Logs for this span" → Loki query filtered by trace_id.

🔗 Trace‑Log correlation (derived fields): In Loki datasource settings → Derived Fields → Name: traceID, Regex: traceID=(\w+), URL: ${__value.raw}, Data source: Tempo. Any log line containing a TraceID becomes a clickable link to the trace.

📊 Prometheus – Metrics Monitoring

Architecture, TSDB, PromQL, and AKS deployment
📖 What is Prometheus?

Open‑source time‑series database and monitoring system. Uses a pull model – it scrapes metrics from HTTP endpoints (exporters).

🏗️ Internal components

Discovery Manager (K8s API, EC2), Scrape Manager (HTTP GET /metrics), TSDB (2h blocks, WAL), Query Engine (PromQL), Alertmanager sender.

▸ Prometheus architecture (text)

📝 PromQL essentials

rate(http_requests_total[5m]) – per‑second average increase (use for counters).
histogram_quantile(0.95, sum(rate(request_duration_bucket[5m])) by (le)) – 95th percentile latency.
sum by (pod) (container_memory_usage_bytes) – aggregated by pod label.

⚠️ Alertmanager – Alert Routing & Notifications

Grouping, inhibition, silences, and receivers
📖 What is Alertmanager?

Handles alerts sent by Prometheus. It deduplicates, groups, silences, and routes alerts to receivers (Slack, PagerDuty, email).

🏗️ Processing pipeline

Prometheus sends alert → Alertmanager receives → group (same alertname/cluster) → inhibit (suppress low‑priority) → silence (maintenance) → route → receiver.

yaml
route:
  group_by: ['alertname', 'cluster']
  group_wait: 10s
  group_interval: 10s
  repeat_interval: 1h
  receiver: 'pagerduty'
  routes:
    - match:
        severity: warning
      receiver: slack
receivers:
  - name: 'slack'
    slack_configs:
      - api_url: 'https://hooks.slack.com/...'
💡 Prometheus rule example: alert: HighErrorRate, expr: sum(rate(http_requests_total{status="500"}[2m])) > 0.05, for: 2m, labels: severity: critical

📜 Loki – Log Aggregation

Architecture, LogQL, and cost‑effective log storage
📖 What is Loki?

Horizontally scalable, cost‑effective log aggregation system. It indexes only labels (pod, namespace), not full text – 10x cheaper than Elasticsearch.

🏗️ Components

Distributor (validates, hashes), Ingester (writes to object storage), Querier (reads from store), Query frontend (splits queries), Compactor (dedupes, retains).

▸ Loki data flow
  Agent (Promtail) → Distributor → Ingester → Object Storage (Azure Blob)
                                         ↑
                                    Querier ← Grafana
📝 LogQL examples

{namespace="prod"} |= "error" – filter logs containing "error".
rate({pod=~"web.*"} | json | line_format "{{.level}}" | = "error" [5m]) – error log rate.
{app="payment"} |~ "trace_id=abc123" – correlate with trace.

📌 Create Azure storage account and container before installing.
bash
az storage account create -n mystorageaccount -g myRG --sku Standard_LRS --kind StorageV2
az storage container create --name loki-chunks --account-name mystorageaccount --auth-mode login

helm repo add grafana https://grafana.github.io/helm-charts
helm upgrade --install loki grafana/loki-stack \
  --namespace loki --create-namespace \
  --set loki.storage.type=azure \
  --set loki.storage.azure.accountName=mystorageaccount \
  --set loki.storage.azure.useManagedIdentity=true \
  --set loki.storage.azure.containerName=loki-chunks \
  --set promtail.enabled=true

Delete: helm uninstall loki -n loki && kubectl delete ns loki

⏱️ Tempo – Distributed Tracing

Architecture, object storage backend, and trace correlation
📖 What is Tempo?

High‑scale distributed tracing backend. It does not index span tags – only trace IDs. Storage cost is linear with number of spans, not number of tags.

🏗️ Components

Distributor (receives OTLP/Jaeger/Zipkin), Ingester (WAL + block flush), Query frontend (trace retrieval), Compactor (Bloom filters).

▸ Tempo data flow
  Instrumented app (OTel) → OTLP → Distributor → Ingester → Object Storage
                                                ↑
                                          Query frontend ← Grafana
bash
az storage container create --name tempo-data --account-name mystorageaccount --auth-mode login

helm upgrade --install tempo grafana/tempo \
  --namespace tempo --create-namespace \
  --set tempo.config.storage.trace.backend=azure \
  --set tempo.config.storage.trace.azure.container_name=tempo-data \
  --set tempo.config.storage.trace.azure.account_name=mystorageaccount \
  --set tempo.config.storage.trace.azure.use_managed_identity=true

Delete: helm uninstall tempo -n tempo && kubectl delete ns tempo

🧰 OpenTelemetry & Collector

Unified instrumentation, OTLP, and collector pipeline
📖 What is OpenTelemetry?

Single set of APIs, SDKs, and tools to generate and collect telemetry data (metrics, logs, traces). Vendor‑agnostic.

🏗️ Collector architecture

Receivers → Processors → Exporters
Receivers: OTLP, Jaeger, Prometheus; Processors: batch, memory_limiter, attributes; Exporters: Prometheus, Loki, Tempo.

yaml
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }
processors:
  batch: {}
exporters:
  prometheus: { endpoint: "0.0.0.0:8889" }
  otlphttp/loki: { endpoint: "http://loki.loki.svc.cluster.local:3100/otlp" }
  otlp/tempo: { endpoint: "tempo.tempo.svc.cluster.local:4317", tls: { insecure: true } }
service:
  pipelines:
    metrics: { receivers: [otlp], processors: [batch], exporters: [prometheus] }
    logs:    { receivers: [otlp], processors: [batch], exporters: [otlphttp/loki] }
    traces:  { receivers: [otlp], processors: [batch], exporters: [otlp/tempo] }
💡 Deploy as DaemonSet (agent) for collecting node logs, or as Deployment (gateway) for central batching.

🐍 Sample instrumented Flask app

Python + OpenTelemetry → traces and logs
python
# app.py – full OpenTelemetry instrumentation
from flask import Flask
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.instrumentation.flask import FlaskInstrumentor
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.sdk.resources import Resource
import logging, time, random

logging.basicConfig(level=logging.INFO, format='{"time": "%(asctime)s", "level": "%(levelname)s", "message": "%(message)s", "traceID": "%(otelTraceId)s"}')
resource = Resource.create(attributes={"service.name": "flask-app"})
trace.set_tracer_provider(TracerProvider(resource=resource))
otlp_exporter = OTLPSpanExporter(endpoint="otel-collector.observability.svc.cluster.local:4317", insecure=True)
trace.get_tracer_provider().add_span_processor(BatchSpanProcessor(otlp_exporter))

app = Flask(__name__)
FlaskInstrumentor().instrument_app(app)

@app.route('/hello')
def hello():
    tracer = trace.get_tracer(__name__)
    with tracer.start_as_current_span("hello-span"):
        time.sleep(random.uniform(0.01, 0.1))
        logging.info("Hello endpoint called", extra={"otelTraceId": trace.get_current_span().get_span_context().trace_id})
        return "Hello, observability!"

@app.route('/slow')
def slow():
    tracer = trace.get_tracer(__name__)
    with tracer.start_as_current_span("slow-span") as span:
        delay = random.uniform(0.5, 2.0)
        span.set_attribute("delay_seconds", delay)
        time.sleep(delay)
        logging.warning("Slow endpoint took %.2f seconds", delay, extra={"otelTraceId": trace.get_current_span().get_span_context().trace_id})
        return f"Waited {delay:.2f}s"

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
dockerfile
FROM python:3.10-slim
WORKDIR /app
RUN pip install flask opentelemetry-distro opentelemetry-exporter-otlp
RUN opentelemetry-bootstrap -a install
COPY app.py .
CMD ["opentelemetry-instrument", "python", "app.py"]
yaml

kind: Deployment

spec:
  replicas: 1
  selector: matchLabels: app: flask-app
  template:
    metadata: labels: app: flask-app

      - name: app

---

  selector: app: flask-app
  ports:
  - port: 5000
    targetPort: 5000
