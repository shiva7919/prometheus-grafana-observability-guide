Monitoring vs Observability

📡 Monitoring

Watching pre-defined metrics and alerting when thresholds breach. Answers "Is something wrong?"

  • Checks known failure modes
  • Dashboard & alert driven
  • Reactive approach
🔬 Observability

Understanding the internal state from external outputs. Answers "Why is something wrong?"

  • Explores unknown unknowns
  • Metrics + Logs + Traces
  • Proactive approach

What is Prometheus?

Open-source monitoring and alerting toolkit originally built at SoundCloud (2012), donated to CNCF in 2016. It is the de-facto standard for cloud-native/Kubernetes monitoring.

🔄 Pull-Based

Prometheus scrapes targets — no agent push needed.

📦 Local TSDB

Stores all data as timestamped float64 values on disk.

🏷️ Dimensional

Key-value labels identify every time-series uniquely.

What is Grafana?

Open-source analytics and visualization platform. Connects to 40+ data sources (Prometheus, Loki, Elasticsearch, MySQL…) and renders interactive dashboards.

Quick Revision Q&A

5 Questions

Monitoring tracks known failure modes via predefined metrics and alerts. Observability allows you to investigate unknown unknowns using the full telemetry data (metrics, logs, traces). Monitoring answers "Is something wrong?" while observability answers "Why is it wrong?"

Pull gives Prometheus control — it decides when and what to scrape. This simplifies firewall rules (scraper opens outbound connections), makes it easy to detect dead targets (no scrape = target down), and centralizes configuration. Push requires agents to know where to send data.

Metrics — Numerical time-series data (Prometheus), Logs — Timestamped text events (Loki), Traces — Request journeys across services (Tempo). Grafana provides a unified view across all three.

Prometheus: 9090, Grafana: 3000, Node Exporter: 9100, Alertmanager: 9093, Pushgateway: 9091.

Each metric: metric_name{label1="val1", label2="val2"} numeric_value [optional_timestamp]
Example: http_requests_total{method="GET", status="200"} 1234

Prometheus Data Model

Every metric is a time-series identified by a name + set of labels:

Data Model 
 http_requests_total { method="GET", status="200", job="api" }  →  1234
 │                     │                                            │
 │                     └── Labels (key-value dimensions)           │
 └── Metric name                                                   └── Float64 value
⚠️
Label Cardinality WarningEach unique label combination = a new time-series in memory. Never use labels with unbounded values like user_id, request_id, or session_id — this causes "cardinality explosion" and OOM crashes.

The Four Metric Types

Counter
Monotonically increasing-only value. Resets to 0 on restart. Always use with rate() or increase().
http_requests_total errors_total bytes_sent_total
Gauge
Can go up or down. Represents a current snapshot of a value. Use directly in queries.
node_memory_MemAvailable_bytes active_connections temperature_celsius
Histogram
Samples observations into configurable buckets. Enables server-side aggregation. Use histogram_quantile().
http_request_duration_seconds request_size_bytes
Summary
Pre-calculates client-side quantiles. Accurate per-instance but cannot be aggregated across instances.
rpc_duration_seconds go_gc_duration_seconds

Instrument your own app using Prometheus client libraries.

python
from prometheus_client import Counter, Gauge, Histogram, start_http_server
import time, random

# Define metrics
REQUEST_COUNT = Counter('app_requests_total', 'Total requests',
                        ['method', 'endpoint', 'status'])
ACTIVE_USERS  = Gauge('app_active_users', 'Active users')
REQUEST_LAT   = Histogram('app_request_duration_seconds', 'Latency',
                          ['endpoint'],
                          buckets=[0.01, 0.05, 0.1, 0.5, 1.0, 5.0])

if __name__ == '__main__':
    start_http_server(8000)   # Expose /metrics on :8000
    ACTIVE_USERS.set(100)
    while True:
        start = time.time()
        time.sleep(random.uniform(0.01, 0.3))
        REQUEST_COUNT.labels('GET', '/api/users', '200').inc()
        REQUEST_LAT.labels('/api/users').observe(time.time() - start)

Quick Revision Q&A

5 Questions

Use Counter for things that only ever increase — request count, error count, bytes sent. Use Gauge for values that can go up or down — memory usage, active connections, temperature.

Each unique label combination creates a new time-series stored in RAM. Labels like user_id with millions of unique values create millions of series — causing "cardinality explosion" that exhausts Prometheus memory and crashes it.

A Histogram creates three sets of time-series: _bucket{le="..."} cumulative counts per bucket, _sum sum of all observations, and _count total observation count. Quantiles are computed server-side using histogram_quantile().

A separate process that translates metrics from a system that doesn't natively speak Prometheus format (e.g., Linux OS, MySQL) into the Prometheus text exposition format at a /metrics HTTP endpoint for Prometheus to scrape.

9100. The metrics are available at http://host:9100/metrics.

Essential PromQL Functions

promql
# ── RATE FUNCTIONS ──────────────────────────────────
rate(http_requests_total[5m])     # Avg per-second rate (smoothed for graphs)
irate(http_requests_total[5m])    # Instantaneous rate (spike-sensitive)
increase(http_requests_total[1h]) # Total increase over window

# ── AGGREGATION ──────────────────────────────────────
sum(rate(http_requests_total[5m]))                     # Total across all
sum by (job, status) (rate(http_requests_total[5m]))   # Keep job + status labels
sum without (instance) (rate(http_requests_total[5m])) # Drop instance label

# ── OTHER AGGREGATORS ────────────────────────────────
avg by (job) (node_cpu_seconds_total)
max by (instance) (node_memory_usage_bytes)
count by (job) (up)       # How many targets per job

# ── HISTOGRAM QUANTILE ───────────────────────────────
histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

Recording Rules

Pre-compute expensive PromQL expressions and save as new metrics — dramatically speeds up dashboards.

yaml
# rules/recording_rules.yml
groups:
  - name: http_metrics
    interval: 30s
    rules:
      # Pre-compute request rate per job
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))

      # Pre-compute CPU utilisation per instance
      - record: instance:node_cpu_utilisation:rate5m
        expr: |
          100 - (avg by (instance) (
            rate(node_cpu_seconds_total{mode="idle"}[5m])
          ) * 100)

      # Pre-compute memory utilisation ratio
      - record: instance:node_memory_utilisation
        expr: |
          1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)
💡
Recording Rule Naming ConventionFormat: level:metric:operations — e.g. job:http_requests:rate5m means aggregated by job, from metric http_requests, using rate over 5m.
❓

Quick Revision Q&A

5 Questions

rate() averages over the entire range window — smoother, good for trend graphs and alerts. irate() uses only the last two data points — more sensitive to spikes, better for detecting sudden bursts.

Recording rules pre-compute PromQL expressions on a schedule and store results as new metrics. They massively speed up Grafana dashboards that repeatedly execute the same complex query, reducing both query time and Prometheus CPU load.

Data is first written to a Write-Ahead Log (WAL) in memory. It gets compacted into 2-hour data blocks on disk. Each block has chunks (compressed data), an index, and metadata. Default retention is 15 days.

It aggregates all time-series matching the query into one series per unique job label value, dropping all other labels. Useful for getting per-service totals.

histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))
This computes the 99th percentile latency across all instances in the last 5 minutes.

Alerting & Alertmanager

Create alert rules in Prometheus and route, group, silence, and deliver notifications through Alertmanager.
AlertsAlertmanagerSlackPagerDutySilences

Alert States

INACTIVE
Condition not met
→
PENDING
Condition met, waiting for duration
→
FIRING
Alert sent to Alertmanager
ℹ️
Why the PENDING state?The for clause prevents false positives from transient spikes. An alert only fires after the condition has been true for the entire duration — e.g. for: 5m means CPU must be above threshold for 5 solid minutes.

Alertmanager Architecture

Alertmanager Processing Pipeline 
  Prometheus
  ────────────▶  ALERTMANAGER
                    │
                    ├─▶ GROUPING      → Bundle related alerts (e.g. 20 nodes → 1 message)
                    │     group_by: [alertname, cluster]
                    │     group_wait: 30s
                    │     group_interval: 5m
                    │
                    ├─▶ ROUTING       → Match alerts to receivers
                    │     severity=critical → PagerDuty
                    │     team=platform    → Slack #platform
                    │
                    ├─▶ SILENCING     → Mute alerts during maintenance
                    │
                    ├─▶ INHIBITION    → Suppress child alerts when parent fires
                    │     critical alert firing → suppress warning for same instance
                    │
                    └─▶ RECEIVERS
                          Email │ Slack │ PagerDuty │ OpsGenie │ Webhook

Alert Rules (prometheus.yml / rules file)

yaml
groups:
  - name: system_alerts
    rules:

      # CPU spike alert
      - alert: HighCPUUsage
        expr: |
          100 - (avg by (instance) (
            rate(node_cpu_seconds_total{mode="idle"}[5m])
          ) * 100) > 90
        for: 5m
        labels:
          severity: warning
          team: platform
        annotations:
          summary: "High CPU on {{ $labels.instance }}"
          description: "CPU is {{ $value | printf \"%.1f\" }}% on {{ $labels.instance }}"
          runbook_url: "https://wiki.example.com/runbooks/high-cpu"

      # Service down
      - alert: ServiceDown
        expr: up == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.job }} is DOWN"
          description: "Target {{ $labels.instance }} has been down for 1+ minutes"

      # High error rate
      - alert: HighHTTPErrorRate
        expr: |
          sum by (job) (rate(http_requests_total{status=~"5.."}[5m])) /
          sum by (job) (rate(http_requests_total[5m])) > 0.05
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "High error rate for {{ $labels.job }}"
          description: "Error rate is {{ $value | humanizePercentage }}"

Alertmanager Configuration

yaml
global:
  resolve_timeout: 5m

route:
  receiver: 'slack-general'
  group_by: ['alertname', 'cluster']
  group_wait: 30s       # Wait 30s to batch alerts
  group_interval: 5m    # Wait 5m between group notifications
  repeat_interval: 4h   # Re-send if still firing after 4h

  routes:
    - match:
        severity: critical
      receiver: 'pagerduty-critical'
    - match:
        team: platform
      receiver: 'slack-platform'

receivers:
  - name: 'slack-general'
    slack_configs:
      - api_url: 'https://hooks.slack.com/services/TOKEN/TOKEN/TOKEN'
        channel: '#monitoring'
        title: '{{ .Status | toUpper }} - {{ .CommonAnnotations.summary }}'
        text: '{{ .CommonAnnotations.description }}'
        send_resolved: true

  - name: 'pagerduty-critical'
    pagerduty_configs:
      - routing_key: 'YOUR_ROUTING_KEY'
        description: '{{ .CommonAnnotations.summary }}'

inhibit_rules:
  # Suppress warning when critical is firing for same instance
  - source_match:
      severity: critical
    target_match:
      severity: warning
    equal: ['alertname', 'instance']

Quick Revision Q&A

5 Questions

PENDING: The alert condition is currently true but hasn't lasted the for duration yet — no notification sent. FIRING: The condition has been true for the full duration — Alertmanager receives the alert and sends notifications.

Bundles multiple related alerts into a single notification. E.g., if 20 nodes go down simultaneously, you receive 1 Slack message instead of 20. Controlled by group_by, group_wait, and group_interval.

A rule that suppresses lower-priority alerts when a higher-priority alert fires for the same target. E.g., suppress a "disk space warning" if "node is completely down" is already firing for the same instance — reduces noise.

Via the Alertmanager UI at http://alertmanager:9093 → New Silence, or via API: POST /api/v1/silences with matchers, start/end time, and a comment. Silences mute alerts matching specified label matchers — used during maintenance windows.

9093. The UI is at http://alertmanager:9093 and the API at http://alertmanager:9093/api/v1/.

RED & USE Methods

🔴 RED Method — For Services
  • Rate — Requests per second
  • Errors — Failed requests per second
  • Duration — Latency distribution (P50/P95/P99)

Best for microservices, APIs, and user-facing endpoints.

🔵 USE Method — For Resources
  • Utilization — How busy is the resource?
  • Saturation — How overloaded / queued?
  • Errors — Are there errors on this resource?

Best for infrastructure: CPU, disk, network, memory.

Quick Revision Q&A

4 Questions

Loki only indexes labels (metadata like job, pod, level), not the log content itself. This makes it significantly cheaper to operate. Trade-off: no full-text search — you use label filters + grep-style content filtering via LogQL.

A single unit of work in a distributed trace — has a name, service, start time, duration, and metadata tags. Multiple spans form a tree representing the complete request journey. The span with the longest duration is usually the bottleneck.

OTLP (OpenTelemetry Protocol) — gRPC on port 4317, HTTP on port 4318. It also supports Jaeger (14268) and Zipkin (9411) protocols.

In Tempo data source settings, configure "Trace to Logs" pointing to Loki with matching tags (e.g., job, pod). Then in Explore, clicking a trace opens a side panel showing logs from that same pod at the same timestamp.

Instrumented Flask App

python — app.py
from flask import Flask, jsonify
from prometheus_client import Counter, Histogram, Gauge, generate_latest
import time, random

app = Flask(__name__)

REQUEST_COUNT   = Counter('http_requests_total', 'Requests', ['method','endpoint','status'])
REQUEST_LATENCY = Histogram('http_request_duration_seconds', 'Latency', ['endpoint'],
                            buckets=[.01,.025,.05,.1,.25,.5,1,2.5])
ACTIVE_REQUESTS = Gauge('http_active_requests', 'Active requests')

@app.route('/api/users')
def users():
    ACTIVE_REQUESTS.inc()
    start = time.time()
    time.sleep(random.uniform(0.01, 0.1))  # Simulate normal work
    REQUEST_COUNT.labels('GET', '/api/users', '200').inc()
    REQUEST_LATENCY.labels('/api/users').observe(time.time() - start)
    ACTIVE_REQUESTS.dec()
    return jsonify({"status": "ok"})

@app.route('/api/slow')
def slow():
    start = time.time()
    time.sleep(random.uniform(2, 5))       # Simulate slow operation
    REQUEST_COUNT.labels('GET', '/api/slow', '200').inc()
    REQUEST_LATENCY.labels('/api/slow').observe(time.time() - start)
    return jsonify({"status": "slow"})

@app.route('/metrics')
def metrics():
    return generate_latest(), 200, {'Content-Type': 'text/plain'}

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)

Prometheus pulls metrics from targets on a schedule. Advantages: central control, easy to detect dead targets (no scrape = down), simpler firewall rules (scraper initiates connections outbound), no agent configuration needed on targets.

Counter — monotonically increasing (requests, errors). Gauge — up/down current state (memory, connections). Histogram — distribution with configurable buckets (latency), aggregatable. Summary — pre-calculated client-side quantiles, not aggregatable.

histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

Run two Prometheus instances with identical configs scraping the same targets. For deduplication and global querying, use Thanos or Cortex. Alertmanager also supports HA with --cluster.peer flags.

Cardinality is the number of unique time-series created by label combinations. High cardinality (user_id, session_id) creates millions of series, exhausting Prometheus RAM and degrading query performance. Each unique label set = one time-series in memory.

Recording rules pre-compute PromQL expressions and save as new metrics — used to speed up dashboard queries. Alert rules evaluate PromQL expressions and fire alerts when conditions are met. Both are defined in rule files loaded by Prometheus.

An ad-hoc query interface for investigating issues without modifying dashboards. You can write PromQL, LogQL, or trace queries directly, switch between Prometheus/Loki/Tempo in one view, and correlate across data sources during incident investigation.

Use Pushgateway — the job pushes its metrics to Pushgateway before exiting, then Prometheus scrapes Pushgateway on its normal interval. Not recommended for long-running services; use direct scraping instead.

RED (for services): Rate (requests/sec), Errors (failed requests), Duration (latency). USE (for resources): Utilization (how busy), Saturation (how overloaded), Errors (error rate). Use RED to diagnose service issues, USE for infrastructure issues.

Prometheus stores numerical time-series metrics (scraped from /metrics endpoints). Loki stores log streams (text) pushed from agents like Promtail. Both use a label-based data model and integrate natively with Grafana.

rate() calculates the average per-second rate over the full range window — smoother, good for alerting and trend graphs. irate() uses only the last two samples — highly sensitive to spikes, good for instant spike detection but noisy on graphs.

A mechanism where a "global" Prometheus scrapes selected/aggregated metrics from multiple lower-level Prometheus instances via their /federate endpoint. Used for hierarchical, multi-datacenter monitoring without sending all raw series to a central instance.
